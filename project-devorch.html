01 — AGENT CONTROL PLANE

DEV
ORCH

AI 코딩 에이전트가 만든 변경을 바로 반영하지 않고, 위험도 분석 → 독립 리뷰 → 테스트 → 사람 승인을 통과한 diff만 새 브랜치에 커밋하는 MCP 서버를 만들었습니다.

TYPEPersonal Project
ROLEDesign · Backend · Evaluation
PERIOD2026.10.08 ~ in progress
STACKPython · MCP (stdio) · Git worktree · Docker
Core question
AI 에이전트가 쓴 코드를, 사람이 승인하지 않으면 반영되지 않게 만들 수 있는가?
Problem

에이전트는 빠르지만, 잘못된 변경도 똑같이 빠르게 들어옵니다.

리뷰가 빠지거나, 테스트가 깨진 채 반영되거나, 에이전트가 승인 단계를 건너뛸 수 있습니다. 그래서 "코드를 잘 쓰게 하는 도구"가 아니라 잘못 동작할 때 멈추게 하는 도구를 목표로 했습니다.

My role

단계를 건너뛸 수 없는 구조를 설계했습니다.

  • 분석·리뷰·테스트·반영을 MCP 도구 8개로 분리. 리뷰가 없거나 NOT_READY면 테스트·반영 도구가 실행을 거부
  • 리뷰·테스트·승인을 모두 diff의 SHA에 묶어, 이후 한 줄이라도 바뀌면 이전 결과를 무효화
  • 승인 도구는 MCP에 두지 않고, 사람이 터미널에서 직접 승인. 승인·작업 기록은 프로젝트 밖의 키로 서명
  • 예상 비용을 먼저 보여주고 실제 비용과 비교, 작업당 비용 상한, 자격증명이 든 diff는 LLM 호출 전에 거부
  • 위험 등급에 따라 다른 모델(Anthropic·OpenAI·Gemini)의 독립 리뷰어를 병렬 배정
System

Analyze → Review → Test → Approve를 하나의 게이트로 연결했습니다.

ANALYZEREVIEWTESTAPPROVE
[REFUSE] run_tests: review missing[INVALID] diff changed after review[STOP] approval_required: HIGH[OK] committed to devorch/<run> branch
Decision

기능보다 "안 되어야 하는 경로"를 먼저 깨 봤습니다.

직접 재현 → 수정

승인 파일 하나를 직접 써서 커밋까지 가는 경로, 정책 파일을 몰래 고쳐 보호를 푸는 경로가 실제로 가능했습니다. 재현한 뒤 승인 기록 서명과 정책 승인 해시로 막았습니다.

안전장치를 일부러 망가뜨려 테스트가 잡는지 확인

최근 기능 5개에서만 33종의 변형을 시험했고, 처음엔 못 잡아 테스트 단언을 고친 경우 3번을 기록에 남겼습니다.

한계는 숨기지 않음

같은 OS 사용자로 실행되는 악의적인 테스트는 서명 키를 읽을 수 있습니다. 샌드박스 없이는 재현됐고, Docker 샌드박스에서는 막히는 것을 실제 Docker로 확인했습니다.

Evidence

실제 저장소와 실제 에이전트로 확인했습니다.

4/4실제 Claude Code가 규칙대로 분석→리뷰→테스트→커밋까지 진행 (작업 4건)
LOW→HIGH분류가 놓친 발행 큐 변경, 보호 경로 추가 후 같은 diff 재현에서 승인 단계로
660수집된 테스트 (33개 파일)
10CI 작업: Windows·macOS·Linux × Python 3.11/3.12, 깨끗한 설치, Docker
표본이 작습니다. 실사용은 내 저장소 algo-pipeline 1곳의 작업 4건과 IDE 승인 흐름 3회입니다. 일반화하지 않습니다.
Measurement

AI 리뷰어가 버그를 얼마나 찾는지도 쟀습니다.

공개 저장소에서 나중에 고쳐진 실제 결함 12개로 리뷰어 구성을 비교했습니다. 판정 기준은 실행 전에 확정하고, 결과를 보고 고치지 않았습니다.

5/12multi(리뷰어 3명) 탐지, 95% 구간 19~68%
3/12single(1명) 탐지, 95% 구간 9~53%
7/12어떤 구성도 못 잡은 결함
$1.55이 평가에 실제로 쓴 비용
결론. 구성 간 차이는 통계적으로 유의하지 않았습니다(p=0.25~0.5). 그래서 DevOrch는 "버그를 잡아 주는 도구"가 아니라 "승인 없이는 반영되지 않게 통제하는 도구"로 정의하고, READY가 안전 보증이 아니라는 문구를 응답마다 남깁니다.
Learning

에이전트의 신뢰성은 막을 수 있는 경로의 목록에서 나옵니다.

리뷰어를 늘리는 것만으로는 탐지율이 확인되지 않았고, 실제로 효과가 확인된 것은 "검토된 diff만 반영", "승인은 사람만", "실패는 통과가 아님" 같은 경계였습니다. 측정하지 않은 것(비용 절감, 다른 팀의 수요)은 미측정으로 남겨 두었습니다.
