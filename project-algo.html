Core question
LLM이 만든 콘텐츠를 무인으로 발행해도 신뢰할 수 있는가?
Problem

생성 성공과 운영 성공은 다릅니다.

LLM 기반 카드뉴스 자동화는 빠르게 만들 수 있지만, 출처에 없는 수치 생성, API 장애에 따른 중복 게시, 테스트 중 운영 DB 오염 같은 문제가 실제 운영 위험으로 이어질 수 있었습니다.

My role

파이프라인을 복원하고 신뢰성 계층을 추가했습니다.

  • 수집·생성·팩트체크·렌더링·발행 파이프라인 복원 및 구조 정리
  • Claim/Evidence 분리와 deterministic·semantic 검증 설계
  • 게시 상태, retry allowlist, idempotency와 rollback 흐름 설계
  • A/B 배정, save_rate_48h, 편집 이력과 guardrail 지표 구현
Decision

규칙으로 판정할 오류와 의미로 판단할 오류를 분리했습니다.

Deterministic Gate

숫자 근거, 필수 필드, 레이아웃 overflow처럼 명확한 오류는 코드로 검사했습니다.

Semantic Critic

문맥 왜곡과 표현 품질처럼 규칙만으로 판정하기 어려운 문제는 의미 기반 평가로 분리했습니다.

Fail-closed

파싱 실패나 근거 부족을 빈 결과로 넘기지 않고, 명시적인 실패 상태로 남기도록 설계했습니다.

System

생성·검증·발행·분석을 하나의 상태 흐름으로 연결했습니다.

COLLECTGENERATEVERIFYOPERATE

Learning

프롬프트보다 실패를 통제하는 구조가 먼저였습니다.

LLM 서비스의 신뢰성은 좋은 프롬프트 하나보다 검증 단계, 실패 상태, 재시도 정책과 관측 가능성에서 결정된다는 점을 배웠습니다.
