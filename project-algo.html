01 — EVIDENCE-BOUND AUTOMATION

ALGO
PIPELINE

뉴스 수집부터 카드뉴스 생성·검증·사람 승인·Instagram 게시 경계·성과 기록까지 연결하되, 검증되지 않은 결과는 다음 단계로 넘기지 않는 AI 콘텐츠 운영 시스템을 설계했습니다.

TYPEPersonal Project
ROLEAI · Backend · Automation
STATUSHardened main / staged rollout
STACKPython · FastAPI · SQLite · LLM API
Core question
LLM 자동화를 어떻게 검증·승인·발행 경계 안에서 운영할 것인가?
Problem

생성 성공과 운영 성공은 다릅니다.

출처에 없는 수치 생성, 검증되지 않은 Queue 항목, 원격 게시 성공 여부가 불확실한 상태의 재시도, 테스트 중 운영 DB 오염은 실제 자동화에서 모두 운영 위험이 됩니다. 그래서 생성 품질만 높이는 대신 각 단계의 근거·상태·권한을 코드로 분리했습니다.

My role

파이프라인을 신뢰성 중심 운영 구조로 재설계했습니다.

  • Queue Lineage V2로 source metadata·schema version·lineage hash 검증
  • Claim/Evidence 분리, deterministic verifier와 Semantic Critic을 이용한 Fact Checker V2
  • publisher 호출 전 durable attempt 기록과 uncertain/stale attempt 자동 재시도 차단
  • 운영 DB와 테스트 DB를 분리하고 CI에서 DB/WAL/SHM 생성 여부까지 검증
  • Instagram Login 인증, read-only account preflight, credential/token 로그 제거
  • Analytics V2의 실험·성과 데이터와 사람 검토 경계를 분리
System

Collect → Verify → Review → Publish를 하나의 상태 흐름으로 연결했습니다.

COLLECTGENERATEVERIFYREVIEW
[BLOCK] unsupported numeric claim[PASS] Queue lineage attestation[SAFE] production DB mutation: 0[OFF] unattended publish by default
Decision

오류를 숨기지 않고 명시적인 실패 상태로 남겼습니다.

Deterministic Gate

숫자 근거, 필수 필드, schema·lineage 불일치처럼 명확히 판정할 수 있는 오류는 코드로 차단합니다.

Semantic Critic

문맥 왜곡이나 근거와 표현 사이의 의미 차이는 의미 기반 검증 단계에서 다시 확인합니다.

Fail-closed publish boundary

계정 불일치, 자격증명 오류, 공개 이미지 URL 미설정, 불확실한 원격 게시 상태에서는 Queue를 소모하거나 자동 재시도하지 않습니다.

Evidence

현재 main 기준으로 운영 경계를 증명합니다.

198Instagram 인증 하드닝 병합 시 전체 테스트
0해당 검증에서 production DB write
BLOCKED근거 없는 숫자 Claim
OFF기본 unattended auto-publish
현재 기준. 초기 Quality Hardening PR #1은 이미 main에 병합됐고 이후 staged rollout, Windows test hardening, public image delivery guard, Instagram Login credential hardening까지 추가 병합됐습니다. 실제 무인 게시 활성화는 별도 운영 승인 경계로 남겨 두었습니다.
Active experiment

다음 단계는 생성량이 아니라 품질 폐루프입니다.

현재 Draft PR #7에서는 근거 기반 생성 → 사람 편집·승인 → 48시간 성과 snapshot → 주간 품질 회고 → 승인 대기 실험 제안으로 이어지는 closed-loop 품질 개선을 검증 중입니다.

이 기능은 아직 Draft이므로 main의 완료 기능처럼 표현하지 않습니다. 최신 PR CI는 통과했지만, 실제 카드뉴스 샘플의 시각 검토 후 병합 여부를 판단하도록 경계를 유지합니다.

Learning

프롬프트보다 실패를 통제하는 구조가 먼저였습니다.

LLM 서비스의 신뢰성은 좋은 프롬프트 하나보다 출처 lineage, 검증 단계, 사람 승인, 재시도 정책과 관측 가능한 상태 전이에서 결정된다는 점을 구현으로 확인했습니다.
